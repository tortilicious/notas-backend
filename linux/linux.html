Linux/VPS · Bloque 0 — El servidor existe

Un VPS con Ubuntu en el que se entra por clave SSH, con un usuario propio sin privilegios permanentes, sin login por contraseña y sin acceso de root por SSH.

Entorno de referencia: Ubuntu 24.04 LTS (imagen minimal) · OpenSSH 9.6. Las directivas y opciones de este documento existen en esa versión; con otra, confírmalas en la documentación de la versión instalada (ssh -V en cada máquina, man sshd_config en el servidor).

Parte 1 · Teoría

1. El VPS y sus vías de acceso

Un VPS (Virtual Private Server) es una máquina virtual alojada en el hardware de un proveedor. Tiene sus propios vCores, memoria y disco reservados, una IP pública y un sistema operativo completo que administras tú. El proveedor entrega la máquina con un usuario root y su contraseña; todo lo demás es trabajo propio.

El panel del proveedor (en Netcup, el SCP) es la vía de gestión que no depende del sistema operativo: desde ahí se instala la imagen, se consultan las huellas de las claves de host y se abre la consola de emergencia.

Vía Depende de la red y de sshd Sujeta a sshd_config Uso
SSH Sí Sí Trabajo diario
Consola VNC del panel No No Recuperación cuando SSH no funciona

La consola VNC equivale a tener un monitor y un teclado enchufados a la máquina. Por eso cualquier usuario con contraseña (incluido root) puede entrar por ella aunque SSH lo prohíba. Es la red de seguridad de todo lo que se cambia en SSH, y se comprueba que funciona antes de necesitarla.

2. Versiones LTS

Ubuntu publica una versión LTS (Long Term Support) cada dos años, en abril de los años pares. Cada LTS recibe cinco años de soporte estándar (parches de seguridad y correcciones).

Versión Salida Fin del soporte estándar Situación
22.04 abril 2022 abril 2027 Muy rodada, pero el soporte se acaba pronto
24.04 abril 2024 abril 2029 Rodada y con margen de soporte
26.04 abril 2026 abril 2031 Demasiado reciente: poca documentación de incidencias y poca presencia en servidores de clientes

Para un servidor se elige la LTS que combine rodaje (problemas ya documentados), margen de soporte y adopción real (lo que vas a encontrar en producción).

Una imagen minimal trae solo lo imprescindible para arrancar y conectarse. Herramientas habituales como nano no vienen instaladas y se añaden con apt según hacen falta.

3. Root frente a usuario propio con sudo

Trabajar como root de forma permanente tiene tres problemas, y un usuario propio en el grupo sudo resuelve los tres:

Problema con root directo Con usuario propio + sudo
Exposición: cualquier comando mal escrito tiene privilegios totales Los privilegios se piden comando a comando, solo cuando hacen falta
Anonimato: todas las acciones aparecen como root sudo registra qué usuario ejecutó qué (journalctl -t sudo)
Contagio: si se compromete un proceso, tiene permisos de root Un proceso comprometido hereda los permisos del usuario

Pertenecer al grupo sudo no da privilegios permanentes: da el derecho a pedirlos autenticándote con tu contraseña. El mecanismo completo (/etc/sudoers, caché de contraseña, su frente a sudo) está en el Bloque 1, §8.

4. SSH: cliente, servidor y sus ficheros

SSH es un protocolo para abrir una shell en otra máquina a través de un canal cifrado. Tiene dos programas:

Pieza Dónde vive Qué hace Su configuración
ssh (cliente) Portátil Inicia la conexión ~/.ssh/config (del usuario), /etc/ssh/ssh_config (de todo el sistema)
sshd (servidor o daemon) VPS Escucha en el puerto 22 y atiende las conexiones /etc/ssh/sshd_config y /etc/ssh/sshd_config.d/

ssh_config y sshd_config se diferencian en una sola letra y configuran programas distintos: la d es de daemon. Editar ssh_config en el servidor para cambiar quién puede entrar no tiene ningún efecto.

En Ubuntu 24.04 el puerto 22 lo abre ssh.socket y ssh.service lanza sshd; el servicio se gestiona como ssh (no sshd). El detalle de la activación por socket está en el Bloque 2, §7.

Ficheros que intervienen a cada lado:

Fichero Máquina Contenido
~/.ssh/id_ed25519 Portátil Clave privada del usuario. Nunca sale de la máquina
~/.ssh/id_ed25519.pub Portátil Clave pública del usuario. Es la que se copia al servidor
~/.ssh/known_hosts Portátil Huellas de los servidores ya aceptados
~/.ssh/config Portátil Alias de conexión y opciones por servidor
/etc/ssh/ssh_host_*_key y .pub VPS Claves de host: identifican al servidor ante los clientes. Las privadas solo las lee root
~/.ssh/authorized_keys VPS (en el home de cada usuario) Claves públicas autorizadas a entrar como ese usuario, una por línea
/etc/ssh/sshd_config VPS Configuración de sshd

5. Autenticación en dos fases

Cada conexión SSH verifica las dos identidades, en este orden.

Fase 1 · El cliente comprueba al servidor. El servidor presenta su clave de host. En la primera conexión el cliente muestra su huella (fingerprint, un resumen corto de la clave) y pide confirmación. Esa huella se coteja con la que publica el panel del proveedor: así sabes que hablas con tu máquina y no con un intermediario. Al aceptarla se guarda en known_hosts y las conexiones siguientes la comprueban solas. Si cambia, SSH se niega a continuar y avisa de un posible ataque man-in-the-middle.

El servidor tiene varias claves de host, una por algoritmo; la huella que se muestra es la del algoritmo negociado, normalmente ED25519.

Fase 2 · El servidor comprueba al usuario. Con clave pública funciona como un reto:

  1. El servidor envía un dato aleatorio, distinto en cada conexión.
  2. El cliente lo firma con la clave privada.
  3. El servidor verifica la firma con la clave pública guardada en authorized_keys. Si cuadra, concede acceso.

La clave privada nunca viaja por la red, ni cifrada. Y como el reto no se repite, capturar el tráfico de una conexión no sirve para suplantarte en otra.

Tipo de clave: ed25519 es el algoritmo recomendado para claves nuevas: claves cortas, rápidas y seguras. Passphrase: cifra la clave privada en el disco del portátil; si alguien roba el fichero sin la frase, no puede usarlo.

6. Métodos de autenticación y las directivas que los controlan

sshd puede ofrecer varios métodos. El cliente prueba los que el servidor anuncia, en orden de preferencia.

Método Qué pide Directiva que lo controla
publickey Firmar el reto con la clave privada PubkeyAuthentication (activo por defecto)
password La contraseña del usuario PasswordAuthentication
keyboard-interactive Preguntas del sistema de autenticación (PAM), que pueden incluir la contraseña KbdInteractiveAuthentication

Para que solo quede la clave hay que cerrar los dos caminos a la contraseña. Con PasswordAuthentication no pero KbdInteractiveAuthentication yes, PAM puede seguir pidiendo la contraseña por la vía interactiva.

Directivas de endurecimiento del bloque:

Directiva Valor Efecto
PermitRootLogin no Root no puede iniciar sesión por SSH con ningún método
PasswordAuthentication no Deja de ofrecerse el método password
KbdInteractiveAuthentication no Deja de ofrecerse keyboard-interactive

Por qué importa: un servidor con IP pública recibe intentos automatizados de adivinar contraseñas desde el primer día. Sin métodos basados en contraseña, esos intentos no tienen dónde probar.

Permisos exigidos. sshd ignora authorized_keys en silencio si el directorio ~/.ssh o el fichero tienen permisos más abiertos de lo debido (directiva StrictModes, activa por defecto): ~/.ssh en 700 y authorized_keys en 600, ambos del propio usuario. La notación octal está en el Bloque 1, §6.

7. Cómo lee sshd su configuración

Tres reglas explican casi todos los «he cambiado la directiva y no hace nada»:

Regla Consecuencia
Gana el primer valor leído Si una directiva aparece dos veces, vale la primera. Al revés que en la mayoría de programas
Include va al principio sshd_config incluye /etc/ssh/sshd_config.d/*.conf en sus primeras líneas, así que esos fragmentos se leen antes y mandan sobre lo que escribas debajo. Algunas imágenes traen ahí un fichero que activa PasswordAuthentication
Match acota hasta el final Todo lo que va detrás de una línea Match se aplica solo a esa condición (un usuario, una IP...). Las directivas globales van antes de cualquier Match

Dos comprobaciones distintas:

Comando Responde a
sudo sshd -t ¿La sintaxis es válida? Silencio significa que sí. No dice qué valor queda
sudo sshd -T ¿Qué valor usa sshd de verdad para cada directiva, después de aplicar Include y el orden?

8. Aplicar cambios sin quedarse fuera

Orden de los pasos. Primero se instala la clave y se comprueba que entras con ella; solo después se desactiva la contraseña. Invertirlo deja la máquina sin acceso por SSH.

La sesión abierta es el salvavidas. Cada sesión SSH cuelga de su propio proceso hijo, independiente del proceso que escucha (la cadena completa está en el Bloque 1, §9). Reiniciar o recargar ssh no corta las sesiones abiertas: por eso se cambia la configuración en una terminal, se prueba desde una segunda terminal y la primera no se cierra hasta confirmar que la segunda entra.

reload frente a restart:

Acción Qué hace con sshd Sesiones abiertas Conexiones nuevas
systemctl reload ssh Le pide releer la configuración sin parar Siguen igual Usan la configuración nueva
systemctl restart ssh Lo para y lo vuelve a arrancar Siguen igual Usan la configuración nueva

Para saber si un cambio se aplicó de verdad no basta con haber escrito el comando: hay que verlo en el sistema. La hora de arranque en systemctl status ssh confirma un restart; una línea Reloading en journalctl -u ssh confirma un reload.

9. La terminal remota: TERM y terminfo

Los programas de pantalla completa (nano, vim, less) necesitan saber qué sabe hacer tu emulador de terminal. Lo averiguan con la variable TERM, que SSH copia del portátil al servidor, y buscando ese nombre en la base de datos terminfo de la máquina donde se ejecutan.

Si el emulador es reciente (Ghostty usa TERM=xterm-ghostty), el servidor no lo conoce y los programas fallan con Error opening terminal. Se arregla copiando la descripción del portátil al servidor:

Dónde se instala Quién la ve Resultado con sudo nano
~/.terminfo del usuario (tic sin sudo) Solo ese usuario Sigue fallando: sudo limpia el entorno y root no mira tu home
Base de datos del sistema (sudo tic) Todos los usuarios, root incluido Funciona

Parte 2 · Ejemplos

La máquina: backend-lab

Proveedor y plan Netcup VPS 500 G12
Hardware 2 vCore · 4 GB DDR5 ECC · 128 GB NVMe
Sistema Ubuntu 24.04 LTS, imagen minimal UEFI amd64
Hostname backend-lab
Usuario miguel, en el grupo sudo
Panel SCP de Netcup (imagen, huellas y consola VNC en Screen)

Ubuntu frente a Debian: Debian es más limpio para aprender, pero Ubuntu es lo que aparece con más frecuencia en despliegues de Odoo. 24.04 frente a 22.04 y 26.04: ver la tabla de §2.

Alias de conexión

# Portátil: ~/.ssh/config
Host vps
    HostName IP_DEL_VPS
    User miguel
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes

HostName es la IP que muestra el SCP. IdentitiesOnly yes hace que el cliente ofrezca solo la clave de IdentityFile, y no todas las que tenga cargadas. A partir de aquí basta ssh vps, y el alias lo usan también scp, rsync y Git.

Las tres directivas en sshd_config

# VPS: /etc/ssh/sshd_config (fragmento, sin # delante y antes de cualquier Match)
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no

Comprobación de cómo quedaron:

miguel@backend-lab ~> grep -n "^PermitRootLogin\|^PasswordAuthentication\|^KbdInteractive" /etc/ssh/sshd_config

La salida debe mostrar cada directiva una sola vez, con su número de línea y el valor no. En backend-lab, /etc/ssh/sshd_config.d/ estaba vacío, así que no había fragmentos que se adelantaran.

Primera conexión: la huella

The authenticity of host 'IP_DEL_VPS' can't be established.
ED25519 key fingerprint is SHA256:...
Are you sure you want to continue connecting (yes/no/[fingerprint])?

Antes de escribir yes, se compara el SHA256:... con la huella ED25519 del SCP. En vez de yes también se puede pegar la huella del panel: el cliente la compara él mismo.

Verificación con ssh -v

Desde una segunda terminal del portátil, con la primera aún abierta en el VPS:

Línea de ssh -v vps Valor que confirma el cierre del bloque
Server host key: ssh-ed25519 SHA256:... Coincide con la huella del SCP
Host '...' is known and matches the ED25519 host key El servidor está en known_hosts
Authentications that can continue: publickey El servidor solo ofrece clave pública
Authenticated to ... using "publickey" La entrada ha sido por clave

Prueba en negativo, forzando la contraseña:

$ ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no vps
miguel@IP_DEL_VPS: Permission denied (publickey).

Entre paréntesis aparecen los métodos que el servidor admite: solo publickey.

El reload que nunca se ejecutó

Tras endurecer SSH parecía que reload no había bastado y que hizo falta restart. Al consultar el journal, no había ninguna línea Reloading en ssh.service ni el comando en el registro de sudo: el reload no llegó a ejecutarse, y el cambio lo aplicó el restart. La lección no es sobre reload, sino sobre el método: una conclusión sobre un servicio se confirma en el journal, no en el recuerdo.

journalctl -u ssh -S '2026-09-11' -U '2026-09-12' | grep -iE 'reload|stopp|start'
journalctl -t sudo -S '2026-09-11' -U '2026-09-12'

3. Redirección y tuberías

Todo proceso tiene dos canales de salida independientes, aunque ambos acaben en tu pantalla:

Canal Número Qué lleva
stdout 1 La salida normal
stderr 2 Errores y diagnósticos
Operador Qué hace
> FICHERO Manda solo stdout al fichero (lo sobrescribe). stderr sigue yendo a la pantalla
2> FICHERO Manda solo stderr al fichero
> FICHERO 2>&1 stderr va al mismo sitio al que apunta stdout en ese momento; ambos acaban en el fichero
| Tubería: la stdout de un comando es la entrada del siguiente
& (al final) Lanza el comando en segundo plano y devuelve la terminal
  • El orden importa. 2>&1 > FICHERO no hace lo mismo que > FICHERO 2>&1: en el primer caso stderr se apunta a la pantalla (donde stdout estaba todavía) y luego stdout cambia al fichero. Escribe siempre > FICHERO 2>&1.
  • El & de 2>&1 significa «el destino del canal», no «el fichero llamado 1». Sin él, 2>1 crearía un fichero llamado 1.
  • /dev/null es un fichero especial que destruye lo que recibe. No es ocultar la salida: el contenido deja de existir. Se usa cuando un comando es muy verboso y solo te importa si falla; con > /dev/null, los errores (stderr) siguen apareciendo.
  • El globbing lo hace la shell, no el comando. Antes de ejecutar rm -rf ./*, la shell sustituye ./* por los nombres de lo que hay dentro. rm recibe una lista de ficheros sueltos, no el asterisco. echo ./* enseña exactamente lo que recibiría. El * no incluye los ficheros ocultos (los que empiezan por .).

4. Jerarquía de ficheros

Todo cuelga de una única raíz, /. Cada directorio principal tiene un uso fijo:

Ruta Contenido
/etc Configuración del sistema
/var Datos que cambian: logs (/var/log), bases de datos, cachés
/home Directorios personales de los usuarios
/root Directorio personal de root
/usr Programas y librerías
/boot Kernel, initramfs y, en máquinas UEFI, el bootloader

5. Discos, particiones y sistemas de ficheros

Son tres capas distintas:

Capa Qué es Ejemplo
Disco El dispositivo (físico, o virtual en un VPS) /dev/nvme1n1 en el portátil; /dev/vda en el VPS
Partición Una división lógica del disco, descrita en la tabla de particiones (hoy, normalmente GPT) /dev/nvme1n1p2
Sistema de ficheros La estructura que organiza ficheros y directorios dentro de una partición btrfs, ext4

Montar es enganchar un sistema de ficheros a un directorio del árbol (el punto de montaje). Hasta que no se monta, existe pero no se puede navegar. Un mismo sistema de ficheros puede estar montado en varios sitios.

Tipo Qué es
ext4 El sistema de ficheros clásico de Linux, con journaling (se recupera tras un corte de luz). El del VPS
btrfs Moderno: compresión transparente, snapshots y subvolúmenes. El del portátil
ntfs El de Windows
fat32 / vfat Sencillo y legible por cualquier firmware. Lo usan la ESP y /boot
tmpfs Vive en RAM; muy rápido; desaparece al reiniciar (/tmp, /run)
proc, sysfs Virtuales: el kernel genera su contenido al leerlos
overlay Lo usa Docker: capas de solo lectura (lowerdir) bajo una única capa de escritura (upperdir); varios contenedores comparten las capas base
linux-swap Espacio de intercambio. zram crea un dispositivo en RAM, comprimido, y lo usa como swap (más rápido que uno en disco)

Subvolúmenes de Btrfs. Una misma partición puede aparecer montada varias veces (/, /home, /var/log…), cada una con su subvolid y su subvol=/@nombre. Son divisiones lógicas de la misma partición que se pueden recuperar (rollback) por separado: se puede volver / a una versión anterior sin tocar /home.

Opciones de montaje (la parte entre paréntesis de la salida de mount):

Opción Significado

noatime No escribe la fecha de último acceso en cada lectura (menos escrituras)

ESP (EFI System Partition): partición fat32 con las banderas boot, esp, donde el firmware UEFI busca el bootloader.

9. Procesos

Proceso. Un programa en ejecución, con un número único, el PID. Todo proceso nace de otro, su padre (PPID). El PID 1 es el primero que lanza el kernel.

Zombie. Proceso que ya terminó pero cuyo padre no ha recogido su estado de salida; sigue en la tabla de procesos, sin consumir recursos. Muchos zombies indican un padre defectuoso.

Hilos del kernel. Los procesos [kworker/…], kthreadd, ksoftirqd… no son programas instalados: son trabajo interno del kernel. Se reconocen porque VIRT, RES y SHR valen 0. En un diagnóstico se ignoran.

Cadena de procesos de una conexión SSH. sshd principal (root, escucha el puerto; nunca atiende conexiones directamente) → un hijo de root que verifica quién eres (sshd: usuario [priv]) → un hijo ya con tu usuario que gestiona la sesión (sshd: usuario@pts/0) → tu shell. Es el patrón de «usar privilegios solo el tiempo necesario». El proceso principal sigue escuchando para la siguiente conexión.

D Dormido esperando disco o red, sin poder interrumpirse

Sufijos de ps s líder de sesión · + en primer plano de su terminal · l con varios hilos

10. Cómo arranca un Linux moderno

Fase Quién Qué hace
1. Firmware UEFI (antes, BIOS) Comprueba el hardware y busca el bootloader en la ESP
2. Bootloader GRUB, systemd-boot… Muestra el menú si hay varias opciones y carga en RAM el kernel y el initramfs; cede el control al kernel
3. Kernel Linux Toma el control del hardware real
4. initramfs El kernel Monta el disco real usando los drivers mínimos que trae este sistema de ficheros temporal
5. Espacio de usuario El kernel lanza systemd como PID 1 systemd arranca el resto
6. Targets y units systemd Arranca los servicios agrupados por fases hasta el target por defecto

Bootloader. Su único trabajo es cargar y entregar el control. No instala ni actualiza kernels: eso lo hace el gestor de paquetes, que además regenera la lista de opciones del menú. Si una opción es otro sistema operativo (Windows), el bootloader hace chainload: le cede el control al bootloader de ese sistema, que arranca su propio kernel.

initramfs. Resuelve un problema de huevo y gallina: el kernel necesita drivers para leer el disco real, pero esos drivers viven normalmente dentro de la partición que aún no puede montar. Se guarda como fichero en /boot y se vuelve a cargar en RAM en cada arranque; no persiste entre arranques, se descarta cuando el disco real está montado. Los gestores de paquetes lo regeneran al actualizar el kernel.

Son dos pasos distintos del kernel, uno detrás de otro: primero usa el initramfs para montar el disco real; después, y sin relación causal con aquel, lanza systemd.

Targets. Un target no ejecuta nada: es un punto de sincronización que agrupa units. Cada uno depende de que otros se hayan alcanzado antes.

Target Qué significa alcanzarlo
sysinit.target Inicialización básica
local-fs.target Sistemas de ficheros locales montados
network.target / network-online.target Red configurada / con conectividad confirmada
nss-lookup.target Resolución de nombres funcionando
basic.target Lo esencial listo: pueden arrancar los servicios normales
multi-user.target Sistema completo en modo texto, listo para login. El normal de un servidor
graphical.target Lo anterior más el entorno gráfico. Innecesario en un servidor sin pantalla
getty.target Prompts de login en las terminales

graphical.target depende de multi-user.target: lo extiende, no lo sustituye. systemctl set-default cambia el target que se persigue al arrancar (crea el enlace /etc/systemd/system/default.target); el cambio se aplica en el siguiente arranque.

SSH no es parte del arranque. sshd es un servicio más: se arranca durante la fase de multi-user.target y se queda escuchando el puerto. Conectarse es un evento posterior e independiente, que puede ocurrir mil veces sin que el sistema vuelva a arrancar.

Medir el arranque

systemd-analyze desglosa el tiempo por fase:

Fase en la salida Qué mide
firmware El UEFI comprobando el hardware físico
loader El bootloader, hasta cargar el kernel
kernel La inicialización del kernel
initrd El initramfs, hasta montar el disco real
userspace systemd arrancando servicios hasta el target por defecto

Una VM no tiene todas las fases. En un VPS no aparecen firmware, loader ni initrd: el hipervisor entrega al kernel un entorno ya preparado, sin hardware físico que comprobar. Por eso un VPS arranca bastante más rápido que un portátil.

systemd-analyze blame lista las units por tiempo de activación. No mide cuánto retrasó cada una el arranque: systemd arranca en paralelo, y una unit lenta puede estar terminando de fondo mientras el sistema ya es utilizable. Las unidades .device que aparecen en un portátil son esperas a que el kernel registre un dispositivo (TPM, puertos serie, particiones del disco con varias rutas alternativas: by-id, by-partuuid, by-path).

El journal y los permisos

journalctl lee el registro de systemd. Sin privilegios solo muestra los mensajes de tu propio usuario, no los del sistema ni los de servicios de otros usuarios; el aviso You are currently not seeing messages from other users and the system lo indica. Se resuelve con sudo o perteneciendo a los grupos adm o systemd-journal. -b limita a un arranque; -u UNIT limita a una unit. Un arranque que lleva días activo acumula todos esos días en -b.

Linux/VPS · Bloque 2 — systemd de verdad

Unit files escritos a mano, targets, dependencias, journalctl con filtros y timers frente a cron.

Entorno de referencia: Ubuntu 24.04 · systemd 255. Las directivas y valores de este documento existen en esa versión; con otra, confírmalos en la documentación de la versión instalada (systemctl --version).

Parte 1 · Teoría

1. Procesos, sesiones y servicios

Proceso. Un programa en ejecución. El kernel le asigna un número, el PID. Todo proceso lo crea otro proceso, su padre; el número del padre es el PPID.

Huérfano. Si el padre muere antes que el hijo, el kernel asigna el hijo al PID 1. Que el PID 1 sea su padre no implica que nadie lo gestione: solo lo ha adoptado.

PID 1. El primer proceso del sistema. En Ubuntu es systemd; /sbin/init es un enlace simbólico a él.

Sesión. Al entrar por SSH se crea una cadena de procesos: sshd de la conexión → shell de login (aparece con guion: -fish, -bash) → los programas que lances. Todo lo lanzado a mano pertenece a esa sesión.

Señales. Avisos cortos que el kernel entrega a un proceso. Ante cada una, el proceso hace la acción por defecto, la captura para hacer otra cosa, o la ignora (salvo SIGKILL).

Señal Número Quién la envía Acción por defecto Uso habitual
SIGHUP 1 La shell, al cerrarse la terminal Terminar Muchos servicios la capturan para releer su configuración (sshd)
SIGINT 2 Ctrl-C Terminar En Python provoca KeyboardInterrupt
SIGTERM 15 kill, systemctl stop Terminar La forma normal de pedir que un programa pare
SIGKILL 9 kill -9, el kernel sin memoria (OOM killer) Terminar sin aviso No se puede capturar ni ignorar

& y nohup. & lanza un programa en segundo plano: libera la terminal, pero el proceso sigue siendo hijo de la shell y muere con ella. nohup hace que el programa ignore SIGHUP y sobreviva al cierre de la sesión, pero queda sin vigilancia: nadie lo reinicia si cae, no arranca tras un reinicio y su salida va a nohup.out.

Servicio. Un programa que gestiona systemd a partir de una unit: un fichero que dice cómo lanzarlo, con qué identidad, cuándo y qué hacer si falla. Un servicio no tiene PID; tiene nombre (labweb.service). Su proceso principal sí lo tiene (Main PID:), y cambia en cada reinicio. Un servicio no tiene terminal.

Daemon. Programa que funciona en segundo plano, sin terminal, esperando trabajo. Que algo sea un daemon no implica que esté gestionado.

2. systemd y las units

systemd arranca el sistema, lanza y vigila los servicios, recoge su salida en el journal y los para al apagar.

Units. Cada cosa que gestiona systemd es una unit. El tipo lo indica la extensión:

Tipo Qué representa
.service Un programa que se lanza y se vigila
.socket Un puerto o socket que systemd abre por adelantado para un servicio
.timer Un momento en el que arrancar un servicio
.target Un punto del arranque que agrupa otras units (multi-user.target)
.scope Procesos que systemd no lanzó pero vigila (las sesiones de usuario: session-N.scope)
.slice Una rama del árbol de grupos de procesos (system.slice, user.slice)

cgroups. systemd coloca cada unit en un grupo de procesos del kernel. Así sabe qué procesos pertenecen a cada unit aunque cambien de padre. Los servicios cuelgan de system.slice; las sesiones, de user.slice/user-UID.slice.

Dónde viven las fichas:

Ruta De quién Prioridad
/etc/systemd/system/ Del administrador Gana
/run/systemd/... Generadas en ejecución, temporales Media
/usr/lib/systemd/system/ De los paquetes; se sobrescriben al actualizar Pierde

Copia en memoria. systemd lee las fichas una vez y trabaja con esa copia. Si editas una, no se entera hasta que ejecutes daemon-reload. Mientras tanto, status avisa con changed on disk.

Estados habituales:

Estado Significado
active (running) El proceso principal está funcionando
active (exited) El proceso terminó con éxito y la unit se considera activa (RemainAfterExit=yes)
active (abandoned) Un scope cuya sesión se cerró pero conserva procesos
inactive (dead) Parado. Normal tras un stop limpio o tras un oneshot
failed Terminó con error, o systemd no pudo lanzarlo

En la línea Loaded: aparece además si la unit está enabled, disabled o static (sin sección [Install]: no se puede habilitar; la arranca otra unit).

3. El unit file de un servicio

Secciones

Sección Qué describe Cuándo la lee systemd
[Unit] Qué es y de qué depende Siempre
[Service] Cómo se ejecuta Siempre
[Install] En qué target se apunta Solo systemctl enable y disable

[Unit] e [Install] son comunes a todos los tipos de unit (servicio, timer, socket). La sección central cambia según el tipo: [Service], [Timer], [Socket].

Reglas de sintaxis

  • Una directiva por línea, Nombre=valor, sin espacios alrededor del =.
  • Los nombres distinguen mayúsculas. Una directiva desconocida o en la sección equivocada se ignora con un aviso en el journal, y la unit arranca igual. Es el tipo de error más peligroso, porque no se ve.
  • Las rutas de ExecStart= van completas: systemd no usa el PATH de tu shell. ExecStart= no es una shell: &, |, > no funcionan.

man systemd.directives es el índice: dice en qué página se explica cada directiva.

Dependencias. Hay dos ejes independientes: dependencia (si una unit arrastra a otra) y orden (cuál arranca antes).

Directiva Al arrancar esta unit Si la otra se para explícitamente Si la otra cae sola
Wants= Arranca la otra Nada Nada
Requires= Arranca la otra Esta se para (y un restart se propaga) Nada
BindsTo= Arranca la otra Esta se para Esta se para
PartOf= — Esta se para o reinicia; solo en esa dirección —
  • After= / Before= solo fijan el orden. Sin After=, systemd arranca las dos a la vez. Lo habitual es Wants= o Requires= junto con After=.
  • Una parada por dependencia es una parada limpia (SIGTERM), así que Restart=on-failure no actúa. Y la unit de la que dependes no arranca a quien depende de ella cuando vuelve.
  • Dependencias por defecto. Todo servicio normal depende de sysinit.target, basic.target, system.slice y systemd-journald.socket, sin escribirlas.
  • Plantillas. Una unit con @ (postgresql@.service) es una plantilla; lo que va entre @ y la extensión (16-main) es la instancia, y dentro de la ficha se usa como %i.

Límite de arranques. Por defecto, si una unit arranca más de 5 veces en 10 segundos (StartLimitBurst=, StartLimitIntervalSec=), systemd deja de intentarlo: Start request repeated too quickly. Protege de los bucles de caídas. Se sale con reset-failed. Van en [Unit] aunque afecten a Restart=, que está en [Service].

Targets. Un target es una etapa del arranque que agrupa units. multi-user.target es el sistema funcionando en modo normal sin entorno gráfico; graphical.target lo incluye y añade el escritorio; sockets.target y timers.target son etapas donde se apuntan sockets y timers. systemctl get-default dice qué target alcanza la máquina.

WantedBy=multi-user.target no hace nada por sí sola. Al ejecutar systemctl enable, se crea un enlace simbólico en /etc/systemd/system/multi-user.target.wants/. Al arrancar, systemd lanza todo lo que hay en esa carpeta. Si el target nunca se alcanza, el servicio nunca arranca solo.

start arranca ahora; enable deja apuntado para los próximos arranques. Son independientes. Una unit sin [Install] es static: no se puede habilitar, solo arrancar a mano o como dependencia de otra.

4. Drop-ins

Un drop-in es un fichero .conf en /etc/systemd/system/<unit>.d/ que se suma a la ficha sin modificarla. Sirve sobre todo para ajustar units de paquetes, cuyos cambios en /usr/lib se perderían al actualizar.

  • Debe repetir la cabecera de sección; sin ella, sus líneas se ignoran.
  • Las directivas de lista (After=, Wants=, Environment=) se acumulan. Las de valor único (User=, Type=) se sustituyen.
  • systemctl status muestra la línea Drop-In: cuando existe alguno.

5. Diagnosticar un servicio que falla

Orden: systemctl status → journalctl -u → la ficha.

Quien hace la acción que falla, escribe el error. systemd lee la ficha, prepara el usuario y lanza el programa. La aplicación abre ficheros, reserva puertos, conecta a bases de datos.

Quién falla Etiqueta en el journal Código de salida Dónde buscar
systemd, al preparar o lanzar systemd[1]: o (programa)[PID]: entre paréntesis 200 en adelante La ficha
La aplicación, ya lanzada programa[PID]: Bajo (1, 2…) Lo que usa el programa

Códigos propios de systemd (man systemd.exec, PROCESS EXIT CODES): 200/CHDIR (no existe WorkingDirectory=), 203/EXEC (no pudo ejecutar el programa), 217/USER (no existe el usuario). Los códigos bajos los define cada programa: en curl, 7 es «no pude conectar»; en el estado del servicio, systemd les pone un nombre (2/INVALIDARGUMENT, 7/NOTRUNNING) que no tiene por qué corresponder a su significado real.

En un bucle de caídas, la causa está en la primera caída de la serie, no en las últimas líneas.

Errores que no hacen fallar el servicio (solo los detectan systemd-analyze verify, el aviso del journal o systemctl show): directivas mal escritas, en la sección equivocada, o una ficha editada sin daemon-reload.

6. El journal

El journal es el registro de systemd. Guarda cada mensaje con campos (_SYSTEMD_UNIT, _PID, _UID, _COMM, PRIORITY, arranque…), que son los que permiten filtrar.

  • Todo lo que un servicio imprime (salida normal y de errores) llega al journal sin que el programa sepa nada de logs.
  • Prioridad. De más a menos grave: emerg, alert, crit, err, warning, notice, info, debug. Lo que imprime un programa llega como info, incluido un traceback: -p err encuentra qué servicio falló (lo marca systemd), no por qué.
  • Persistencia. Si existe /var/log/journal, el journal conserva los arranques anteriores. En Ubuntu es persistente por defecto.
  • La hora es la de llegada. Con el búfer de Python, un mensaje puede llegar mucho después de imprimirse. Python retiene su salida cuando no escribe en una terminal; PYTHONUNBUFFERED=1 o python3 -u lo desactivan.
  • Un log dice lo que el programa cree que pasa. Si un programa anuncia algo antes de hacerlo, el log puede afirmar lo que luego falla.
  • Permisos. Para leer los mensajes del sistema sin sudo, el usuario tiene que estar en el grupo systemd-journal.

7. Activación por socket

Una unit .socket hace que systemd abra un puerto por adelantado y se lo pase al servicio con su mismo nombre. Con Accept=no, un único proceso recibe el puerto y atiende todas las conexiones; con Accept=yes, se lanza un proceso por conexión. Si el servicio está parado y llega una conexión, systemd lo arranca (TriggeredBy: en el status del servicio).

Consecuencias: en ss, el puerto aparece en manos de systemd (PID 1) y del servicio; y el puerto lo decide la unit .socket, no la configuración del programa.

8. Timers y cron

Un timer arranca el servicio con su mismo nombre en un momento dado. El timer dice cuándo; el servicio, qué. Para tareas que hacen algo y terminan, el servicio usa Type=oneshot, y no necesita [Install]: se habilita el timer.

Directiva del timer Qué hace

RandomizedDelaySec= Retraso aleatorio, para repartir la carga
WantedBy=timers.target En [Install], para habilitar el timer

cron lee una tabla de tareas por usuario (crontab), con cinco campos de tiempo: minuto, hora, día del mes, mes, día de la semana. Envía la salida de cada tarea por correo; sin servidor de correo (MTA), la descarta. No registra si la tarea falló.

Parte 1 · Teoría

1. Interfaces y direcciones

Una interfaz es un punto por el que la máquina envía y recibe tráfico. Un VPS típico tiene dos:

Interfaz Qué es Direcciones Quién puede llegar
lo (loopback) Interfaz virtual: la máquina hablando consigo misma 127.0.0.1/8, ::1/128 Solo la propia máquina
eth0 La interfaz conectada a la red del proveedor IPv4 e IPv6 públicas Cualquiera en internet

Una máquina tiene varias direcciones a la vez, una o más por interfaz. Un paquete dirigido a 127.0.0.1 nunca sale de la máquina que lo envía: cada equipo usa esa dirección solo para sí mismo, y no existe camino por internet hasta la 127.0.0.1 de otro.

Para qué sirve lo. Para que los programas de una misma máquina se comuniquen por red sin exponerse: Odoo con PostgreSQL, nginx con Odoo, cualquier programa con el stub de DNS. Tres ventajas: lo interno no es alcanzable desde fuera; un programa que habla TCP con 127.0.0.1 habla igual con otra máquina cambiando solo la dirección; y funciona aunque eth0 esté caída.

TCP no significa «desde fuera». TCP es un protocolo de conexión y funciona igual entre dos máquinas que dentro de una sola, usando 127.0.0.1.

Máscara y red. 89.58.45.111/22 significa 22 bits de red y 10 de host (1024 direcciones). Aplicando la máscara (255.255.252.0) se obtiene la red 89.58.44.0/22, que va de 89.58.44.0 a 89.58.47.255 (broadcast, el brd de la salida). Las demás máquinas de ese rango son vecinas: se alcanzan directamente.

Ámbito de una dirección IPv6:

scope Significado
global Pública, alcanzable desde internet. Es la que va en un registro AAAA
link De enlace local (fe80::...): solo vale dentro del segmento físico. Toda interfaz IPv6 tiene una
host Solo dentro de la máquina (::1)

Estado de una interfaz: UP = activada por software; LOWER_UP = enlace físico presente («cable conectado»). Una interfaz puede tener varios nombres (altname): eth0, ens3 y enp0s3 pueden ser la misma.

2. Rutas

Una ruta es una regla: «para tal destino, entrégalo de tal manera». El kernel elige la ruta según el destino de cada paquete; si varias encajan, gana la más concreta.

Elemento Significado
via IP Se entrega a un intermediario (el siguiente salto o puerta de enlace), que lo reenvía. Sin via, entrega directa al destino
dev eth0 Por qué interfaz sale
default Equivale a 0.0.0.0/0 (IPv4) o ::/0 (IPv6): una máscara de cero bits abarca todas las direcciones. Es la ruta de «todo lo demás»
scope link El destino está en el mismo enlace: entrega directa
proto kernel La creó el kernel al asignar una dirección a la interfaz (por ejemplo, la ruta a la propia red /22)
proto static Viene de una configuración estática escrita en un fichero
proto dhcp La entregó un servidor DHCP
src IP Dirección que se usa como remitente

Con una sola interfaz real, todo sale por eth0: lo único que decide la tabla es el siguiente salto (el vecino directamente o el router). La elección de interfaz importa cuando hay varias (docker0 con Docker, wg0 con WireGuard).

La puerta de enlace tiene que estar dentro de la red de la interfaz; si no, el VPS no sabría llegar a ella. En IPv6 es habitual que sea una dirección de enlace local (fe80::1); como no pertenece a la red /64, la ruta necesita marcarla como alcanzable en el mismo enlace (on-link: true en netplan, GatewayOnLink=true en systemd-networkd).

Puerta de enlace virtual (VRRP). En los centros de datos, la puerta de enlace suele ser una IP virtual compartida por dos o más routers físicos: contesta uno y, si cae, otro asume la dirección sin que los clientes noten nada. El VPS envía a la IP virtual, pero traceroute muestra la IP propia del router físico que responde. Se reconoce en la tabla de vecinos por la MAC: 00:00:5e:00:01:XX (IPv4) y 00:00:5e:00:02:XX (IPv6) están reservadas para VRRP. keepalived, la herramienta estándar de alta disponibilidad en Linux, usa el mismo protocolo.

Tabla de vecinos. Asocia cada IP de la red local con la MAC que respondió por ella.

Estado Significado
REACHABLE Confirmado hace poco
STALE La MAC se conoce, pero hace tiempo que no se confirma; se volverá a comprobar al usarla
FAILED Se preguntó por esa IP y nadie respondió

Lectura de traceroute. Varias IP en un mismo salto: las sondas fueron por caminos paralelos (reparto de carga). *: esa sonda no obtuvo respuesta (los routers limitan las respuestas; no implica pérdida). Un salto que «tarda» más que el siguiente no indica distancia: generar respuestas a traceroute es tarea de baja prioridad para un router.

El servicio que aplica la red lo indica la clave renderer:; sin ella, en Ubuntu Server es systemd-networkd.

Por qué existe netplan si systemd-networkd ya tiene su formato (.network, con secciones como los unit files, documentado en man systemd.network): un solo formato vale para servidores (systemd-networkd) y escritorios (NetworkManager); es lo que generan las herramientas de la nube (cloud-init); y netplan try aplica un cambio y lo deshace solo si no se confirma, lo que evita perder SSH por un error.   • Los ficheros de netplan deben ser legibles solo por root (600), porque pueden contener secretos (contraseñas wifi, claves de VPN).
  • Configuración estática: el YAML lista addresses. Por DHCP: dhcp4: true y sin lista de direcciones.

4. Sockets: quién escucha y desde dónde se llega

Socket que escucha. Un programa que espera conexiones reserva una dirección y un puerto de la propia máquina.

Columna de ss Significado
Local Address:Port El extremo de esta máquina: en qué dirección y puerto escucha el programa
Peer Address:Port El otro extremo: quién está conectado. En un socket que escucha sale * porque todavía no hay nadie
State LISTEN (TCP esperando), UNCONN (UDP: no tiene conexiones, es su equivalente), ESTAB (conexión establecida)

La dirección local decide desde dónde se puede llegar:

Dirección local Atiende en Alcanzable desde fuera
127.0.0.1, [::1], o lleva %lo Solo la interfaz loopback No
Una IP pública concreta Solo esa dirección Sí
0.0.0.0 (IPv4) / [::] (IPv6) Todas las direcciones de la máquina Sí

0.0.0.0 se refiere a las direcciones de la propia máquina, no a quién se conecta. El peer no es una regla de admisión: solo registra quién está al otro lado. El filtrado por cliente se hace en el firewall o en la propia aplicación (pg_hba.conf en PostgreSQL).

Cómo entrega el kernel una conexión entrante:

  1. Llega un paquete dirigido a IP:puerto. El puerto lo elige el cliente (22 para SSH, 80/443 para un navegador).
  2. El kernel busca un socket que escuche con ese puerto y con esa IP (o con 0.0.0.0).
  3. Si lo encuentra, entrega la conexión a ese programa. Si no, la rechaza (Connection refused).

Un programa en 127.0.0.1:8080 no recibe lo que llega a IP_pública:8080: coincide el puerto, pero no la dirección.

Cada conexión se identifica con cuatro datos: IP y puerto locales, IP y puerto del peer. Así se distinguen dos clientes conectados al mismo puerto. El cliente usa un puerto alto aleatorio en su lado. Desde una red doméstica, el peer que ve el servidor es la IP pública del router, no la del equipo (NAT).

Socket Unix. Una puerta de conexión en forma de fichero (por ejemplo, /var/run/postgresql/.s.PGSQL.5432), solo usable desde la misma máquina. Como la conexión ocurre dentro del sistema, el sistema operativo sabe qué usuario está al otro lado; por TCP, el servidor solo ve una IP y un puerto. En ss, la dirección local de un socket Unix es una ruta; el número que aparece después es un identificador interno, no un puerto.

6. Bibliotecas, cabeceras y compilación

Compilar es traducir un programa escrito en un lenguaje como C al código que entiende el procesador. Python no se compila, pero algunas librerías Python tienen partes en C por velocidad.

Biblioteca: código ya escrito que reutilizan muchos programas (libpq: cómo hablar con PostgreSQL).

Estática (.a) Compartida (.so)
Cuándo se une al programa Al compilar: se copia dentro Al ejecutar: se busca en el sistema
El programa resultante Más grande, autosuficiente Más pequeño; depende de que la biblioteca esté instalada
Parche de seguridad Hay que recompilar cada programa Se actualiza un fichero y todos lo usan al reiniciarse

Los programas piden un nombre con la versión de su interfaz (libpq.so.5), que es un enlace a la biblioteca real (libpq.so.5.16). Así se puede actualizar la biblioteca sin que los programas se enteren. Go compila por defecto en estático: un binario de Go funciona en un contenedor casi vacío.

Cabecera (.h): el índice de lo que ofrece una biblioteca: nombres de funciones, qué datos reciben y qué devuelven. No contiene el código. El compilador la necesita para traducir una llamada a esa biblioteca sin tener su código fuente; una vez compilado el programa, deja de hacer falta. C las usa porque resuelve todo antes de ejecutar; Python, que resuelve los import al ejecutar, no las necesita; Go y Rust leen la información directamente del paquete que importan.

Paquetes -dev: traen las cabeceras (y herramientas como pg_config) para compilar contra una biblioteca. El paquete sin -dev trae la biblioteca para ejecutar.

Paquete Contiene Hace falta
libpq5 libpq.so.5 Siempre que un programa use PostgreSQL (psql, Odoo funcionando)
libpq-dev libpq-fe.h, pg_config Solo al compilar algo que use libpq (psycopg2)
libpython3.12-dev Python.h Al compilar extensiones en C de Python
libldap-dev lber.h y demás cabeceras de LDAP Al compilar python-ldap

Cadena de herramientas. Un compilador es una cadena: gcc traduce C a ensamblador, as (ensamblador) lo convierte en código del procesador y ld (enlazador) lo une con las bibliotecas. gcc viene en gcc-x86-64-linux-gnu (y sus dependencias); as y ld, en binutils. El metapaquete build-essential trae la cadena completa (gcc, g++, make, libc6-dev). En el nombre x86_64-linux-gnu-gcc, la primera parte indica para qué sistema genera programas; los nombres con versión (-13) o con otro prefijo (aarch64-...) son otras versiones u otros procesadores.

8. PostgreSQL preparado para un servicio

Rol: el usuario dentro de PostgreSQL. Para entrar sin contraseña por el socket, el rol debe llamarse igual que el usuario de Linux.

Privilegios mínimos del rol odoo: CREATEDB (Odoo crea y duplica bases desde su interfaz). Ni SUPERUSER (podría leer y borrar cualquier base y ejecutar comandos como postgres) ni CREATEROLE. Ser propietario de una base no es un privilegio que se otorgue: es la consecuencia de haberla creado.

pg_hba.conf: en Ubuntu, /etc/postgresql/16/main/pg_hba.conf. Cada fila es una regla; se leen de arriba abajo y se aplica la primera que encaje en las cuatro primeras columnas. Las líneas con # son comentarios.

Columna Significado Valores habituales
TYPE Por dónde llega la conexión local (socket Unix), host (TCP)
DATABASE A qué base all, una concreta, replication
USER Qué rol all o uno concreto
ADDRESS Desde qué IP (solo en host; vacía en local) 127.0.0.1/32, ::1/128
METHOD Cómo se comprueba la identidad peer, scram-sha-256
Método Funcionamiento
peer Pregunta al sistema qué usuario de Linux hay al otro lado del socket y deja entrar como el rol del mismo nombre. Sin contraseña. Solo con local
scram-sha-256 Contraseña comprobada sin enviarla en claro

Una fila se lee como: «si la conexión llega por TYPE, a la base DATABASE, como el rol USER, desde ADDRESS, compruébalo con METHOD».

Sin host, los programas que usan libpq se conectan por el socket Unix. Por eso Odoo no llevará host de base de datos en su configuración: entra por peer y no hay ninguna contraseña de base de datos guardada en un fichero. La fila host ... 127.0.0.1/32 existe para programas que solo hablan TCP, como un túnel SSH desde otro equipo.

PostgreSQL en Debian/Ubuntu va por versiones: cada versión tiene su paquete (postgresql-client-16), sus programas en /usr/lib/postgresql/16/bin/ y su configuración en /etc/postgresql/16/main/. /usr/bin/psql es un enlace a pg_wrapper (paquete postgresql-client-common), que lanza el psql de la versión adecuada.

9. Disposición de una instalación a mano

Regla general: el código es de root; los datos, del usuario del servicio.

Pieza Ruta Dueño Por qué
Código de Odoo /opt/odoo/src root Solo modificable con sudo, de forma deliberada. Si alguien aprovecha un fallo de Odoo, no puede reescribir Odoo
Entorno virtual /opt/odoo/venv root Igual que el código. Se puede borrar y recrear sin tocar el código
Datos (adjuntos, sesiones) /var/lib/odoo odoo Odoo necesita escribir ahí. /var/lib es el sitio estándar para los datos que genera un programa

Separar código, entorno y módulos propios evita que git vea el entorno como ficheros extraños y que una actualización de Odoo pise módulos propios.

Usuario de sistema: UID bajo, shell nologin, sin sesión. sudo -u odoo comando ejecuta un comando como ese usuario aunque tenga nologin, porque no abre una sesión.

Clon superficial. --depth 1 descarga solo la última versión de cada fichero; el historial aparece como grafted. El commit desplegado se anota para poder reproducir la instalación exacta.

dubious ownership. Git se niega a trabajar en un repositorio que pertenece a otro usuario, porque podría llevar configuración que ejecute programas. Se ejecuta con sudo (como el dueño) o se declara de confianza con safe.directory.

10. Permisos de un fichero con secretos

Linux decide qué puede hacer un usuario con un fichero mirando tres categorías, en este orden, y aplica la primera que encaja:

Categoría Letra en chmod Quién entra
Propietario u (user) Un único usuario
Grupo g (group) Los miembros del grupo del fichero
Otros o (others) Todos los demás
Las tres a (all) —

Cada categoría tiene tres permisos. En ls -l aparecen como nueve caracteres, tres por categoría; en forma numérica, cada cifra es la suma de los permisos concedidos:

Permiso Letra Valor En un fichero En un directorio
Leer r 4 Ver el contenido Listar lo que contiene
Escribir w 2 Modificarlo Crear y borrar dentro
Ejecutar x 1 Ejecutarlo como programa Atravesarlo para llegar a lo que hay dentro
Nada - 0

chmod admite dos formas:

Forma Ejemplo Efecto
Numérica chmod 640 Fija los nueve permisos: rw-r-----
Simbólica chmod o-r Modifica solo lo indicado (+ añade, - quita, = fija esa categoría) y deja el resto como estaba

Con la forma simbólica hay que saber de qué permisos se parte: g+r sobre un fichero que ya es rw-r--r-- no cambia nada. touch crea los ficheros con rw-r--r--, legibles por todos.

Patrón para un fichero de configuración con secretos: propietario root (lectura y escritura), grupo el del servicio (solo lectura), otros nada → root:servicio con 640. El servicio lee su configuración pero no la cambia; un usuario sin sudo no la ve. Los permisos se fijan antes de escribir el secreto.

Atravesar directorios. Para llegar a un fichero hay que tener x en todos los directorios de su ruta. Un directorio con rwxr-x--- deja fuera a otros aunque lo que haya dentro tenga permisos más abiertos.

Editar ficheros protegidos. sudoedit copia el fichero a un temporal, lo abre con el editor del usuario normal y, al salir, lo copia encima del original conservando propietario, grupo y permisos. El editor no se ejecuta como root, a diferencia de sudo vim.

Alias de la shell. Si ls es un alias de un sustituto (como eza), su salida no es la estándar: puede ocultar el grupo o marcar los ficheros con . en lugar de -. command ls ejecuta el programa real. Con sudo delante también se ejecuta el real, porque los alias son de la shell y sudo no los conoce.

11. Opciones de Odoo: línea de comandos y odoo.conf

Odoo se ajusta con opciones de odoo-bin. Todas, menos unas pocas, pueden escribirse también en un fichero de configuración, que es la línea de comandos guardada de forma permanente.

Cómo leer una opción en la referencia o en --help:

Trozo Ejemplo Significado
Forma corta -c Se escribe -c valor
Forma larga --config Se escribe --config=valor o --config valor
Hueco del valor <config>, CONFIG Lo que hay que poner; los < > no se escriben

Las opciones van detrás del programa al que pertenecen. En sudo -u odoo /opt/odoo/venv/bin/python /opt/odoo/src/odoo-bin -c /etc/odoo/odoo.conf hay tres programas encadenados: -u odoo es de sudo, Python no lleva opciones y -c es de Odoo. Una opción que espera valor no funciona sola.

Formato del fichero:

[options]
nombre = valor
  • La sección [options] es obligatoria y va en minúsculas. Con [Options], Odoo no encuentra la sección e ignora el fichero entero sin dar error.
  • Los espacios alrededor de = son opcionales.

Del nombre de la CLI al nombre del fichero: se quita el -- y los - pasan a _ (--http-interface → http_interface). La referencia lista las excepciones; la que más aparece es --database → db_name. La fuente definitiva es odoo/tools/config.py: el valor de dest= de cada opción es su nombre en el fichero. Algunas opciones solo existen en el fichero, como admin_passwd.

Qué fichero lee Odoo: sin -c, $HOME/.odoorc del usuario que lo ejecuta. Con -c RUTA, ese. El log lo confirma con la línea Using configuration file at RUTA; si no aparece, Odoo está usando los valores por defecto. --save hace que Odoo escriba su configuración en el fichero: con root:odoo 640, no puede.

http_port --http-port (-p) 8069 Puerto HTTP

Odoo añade siempre DATA_DIR/addons/18.0 a las rutas de módulos, para los que se descargan desde la propia interfaz, y siempre incluye odoo/addons, los módulos base.

Contraseña maestra. Protege el gestor de bases (/web/database/manager): crear, duplicar, descargar copia, restaurar y borrar bases. No sirve para entrar en Odoo: para eso está el usuario de cada base. Con el valor por defecto, admin, el gestor avisa de que no está protegido. En el fichero puede ir en texto plano, protegida por los permisos, o cifrada.

13. Túnel SSH: reenvío de puertos

Un servicio que escucha en 127.0.0.1 del servidor no es accesible desde fuera. Para usarlo desde otro equipo sin abrir ningún puerto, se reenvía un puerto local a través de la conexión SSH:

ssh -N -L PUERTO_LOCAL:DESTINO:PUERTO_DESTINO SERVIDOR
Parte Significado
-L Reenvío de puerto local: se abre PUERTO_LOCAL en el equipo desde el que se lanza
PUERTO_LOCAL Cualquiera libre por encima de 1023. Si el habitual está ocupado, se elige otro; solo cambia la dirección del navegador
DESTINO:PUERTO_DESTINO A dónde se conecta el servidor al recibir algo por el túnel. Se interpreta desde el servidor: 127.0.0.1 es el propio servidor
-N Sin shell remota, solo el túnel. La terminal queda sin prompt; Ctrl+C lo cierra

Camino de una petición:

Tramo Origen → destino Lo que ve el servidor
Equipo local → servidor IP pública de casa → IP_servidor:22 Una conexión SSH más
Dentro del servidor sshd → 127.0.0.1:PUERTO_DESTINO Una conexión local

Para el servicio, la petición llega desde 127.0.0.1, enviada por sshd. Por eso el túnel funciona con servicios que solo aceptan conexiones locales, y la IP del cliente solo aparece en las conexiones del puerto 22.

Un servicio interno se queda en 127.0.0.1 de forma permanente: hoy se accede por túnel; más adelante, un proxy inverso en la misma máquina será la única puerta hacia fuera.

14. Odoo como servicio de systemd

Por qué muere al cerrar la terminal. Un programa lanzado a mano cuelga de la sesión SSH (en status aparecería bajo user.slice/.../session-N.scope). Al cerrarse la sesión, sus procesos reciben SIGHUP y mueren. Lanzado por systemd, cuelga de system.slice/odoo.service y no depende de ninguna sesión: es la línea CGroup: de systemctl status.

Dónde va la unit. systemd busca units en varias carpetas; la de más prioridad gana si hay dos con el mismo nombre:

Carpeta Quién escribe Prioridad
/etc/systemd/system/ El administrador La más alta
/run/systemd/system/ Units temporales; se borran al reiniciar Media
/usr/lib/systemd/system/ Los paquetes de apt La más baja

Un servicio instalado a mano lleva su unit en /etc/systemd/system/; en /usr/lib podría pisarla una actualización. La carpeta es de root, así que la unit se crea con sudo y queda root:root 644: puede leerla cualquiera porque no contiene secretos (están en odoo.conf, 640). La ruta desde la que systemd cargó una unit es la propiedad FragmentPath. Referencia: man systemd.unit, apartado UNIT FILE LOAD PATH.

Del comando manual a la unit. Cada parte del arranque manual tiene su directiva:

Comando manual Directiva Sección

/opt/odoo/venv/bin/python /opt/odoo/src/odoo-bin -c /etc/odoo/odoo.conf ExecStart= con la línea completa: ejecutable y, detrás, sus argumentos [Service]
  • ExecStart= admite argumentos separados por espacios, pero no es una shell: rutas completas y nada de |, > o & (man systemd.service, apartado COMMAND LINES).
  • Los nombres de directiva y de sección distinguen mayúsculas: Execstart= o [Instal] se ignoran con un aviso y la unit queda incompleta.
  • Sin Group=, se usa el grupo por defecto del usuario: User=odoo da odoo:odoo, igual que sudo -u odoo. Los grupos suplementarios salen de la base de usuarios (man systemd.exec, User=, Group=).

Type=: cuándo se considera arrancado. Odoo lanzado a mano no devuelve el prompt: se queda en primer plano. Corresponde a simple o exec, no a forking (programas que se van a segundo plano).

15. Umask: los permisos de lo que se crea

Un programa que crea una carpeta pide normalmente 777 (666 si es un fichero). Antes de crearla, el kernel le quita los permisos que indica la umask del proceso. La umask no concede nada: solo quita.

0  0  2  7
│  │  │  └─ otros
│  │  └──── grupo
│  └─────── propietario
└────────── cifra especial (casi siempre 0)

Cada cifra usa los valores de los permisos (r = 4, w = 2, x = 1) con el sentido contrario: lo que aparece se quita. 0 no quita nada, 2 quita escribir, 7 quita todo.

umask Carpeta nueva Fichero nuevo Grupo Otros
0002 775 rwxrwxr-x 664 Escribe Lee
0022 755 rwxr-xr-x 644 Lee Lee
0027 750 rwxr-x--- 640 Lee Nada
0077 700 rwx------ 600 Nada Nada

De dónde la saca un proceso. La hereda de quien lo lanza. La shell de un usuario de Ubuntu suele tener 0002; un servicio de systemd recibe 0022 si la unit no dice otra cosa (UMask= en man systemd.exec). El mismo programa crea carpetas con permisos distintos según cómo se arranque. Odoo lanzado desde la shell creó filestore con 775.

Solo afecta a lo nuevo. Cambiar la umask no toca lo que ya existe; para igualarlo se usa chmod.

Por qué los demás pueden leer por defecto. Es la tradición de Unix: casi todo es legible y solo se protege la escritura. Para datos privados hay que cerrarlos con algo: el directorio de arriba (sin x para otros, nadie lo atraviesa), la umask, o las dos cosas.

Criterio para los datos de un servicio: 0027. Propietario escribe, grupo lee, otros nada: el mismo criterio que /var/lib/odoo (750) y odoo.conf (640). Los datos siguen cerrados aunque un día cambien los permisos del directorio de arriba, y el grupo del servicio queda como vía de solo lectura (por ejemplo, para un usuario de copias de seguridad) sin recurrir a root. Root no cuenta en este cálculo: lee y escribe cualquier cosa.

16. Dependencias externas de un módulo

Odoo se divide en el núcleo (el código de /opt/odoo/src/odoo) y en módulos (carpetas como addons/account_peppol). Un módulo puede necesitar bibliotecas de Python que el núcleo no trae. Las declara en su ficha, el fichero __manifest__.py de su carpeta:

'external_dependencies': {
    'python': ['phonenumbers'],
},

Odoo lee esa clave al instalar el módulo. Si la biblioteca no está en el entorno de Odoo, la instalación se detiene con un error. Ese entorno es /opt/odoo/venv, no el Python del sistema.

Concepto Qué es Dónde vive Ejemplo
Módulo Una funcionalidad de Odoo, con su código y su ficha Carpeta con __manifest__.py account_peppol
Biblioteca de Python Código de terceros que el módulo importa Paquete instalado en el entorno de Odoo phonenumbers
Declaración Lista de bibliotecas que el módulo exige Clave external_dependencies del manifest 'python': ['phonenumbers']

Que una biblioteca aparezca en requirements.txt del núcleo significa que Odoo la necesita para arrancar. Que aparezca solo en el manifest de un módulo significa que hace falta únicamente para ese módulo. Son dos listas distintas, y el error de instalación habla de la segunda.

17. Informes PDF: wkhtmltopdf

Odoo no genera los PDF por sí mismo. Monta cada informe como HTML y se lo entrega a un programa externo, wkhtmltopdf, que lo convierte en PDF. Si el programa no está, Odoo muestra el informe en HTML.

El programa. wkhtmltopdf funciona como un navegador sin ventana: carga la página y la dibuja en PDF. Su motor de dibujo es Qt WebKit, un componente antiguo. El proyecto está archivado desde 2023: no publica versiones nuevas ni corrige fallos. Odoo 18 lo sigue necesitando. No encontramos un sustituto incluido en el núcleo; las alternativas que existen son módulos de terceros, algunos de pago, y no se han evaluado.

Dos builds. El build de Ubuntu no lleva el parche de Qt y no pone cabecera ni pie en los PDF. El build oficial sí.

Dónde se decide la dirección de los recursos. wkhtmltopdf pide por HTTP los estilos, el logo y las fuentes que la página enlaza, igual que un navegador. 18. nginx como proxy inverso

Servidor web. Un programa que escucha en un puerto (80 para HTTP, 443 para HTTPS) y atiende peticiones HTTP. Puede servir ficheros del disco o reenviar las peticiones a otro programa.

Proxy. Un intermediario: recibe una petición, la hace en nombre de otro y devuelve la respuesta. Los dos extremos no hablan directamente.

Proxy directo (forward) Proxy inverso (reverse)
Trabaja para Los clientes Los servidores
Dónde está Cerca de los clientes (la red de una empresa) Cerca de los servidores (el VPS)
Quién sabe que existe El cliente lo configura a propósito El cliente no lo sabe: cree que habla con el servidor
Qué oculta Al cliente: el servidor ve la IP del proxy Al servidor: el cliente solo ve el proxy
Ejemplo Proxy de oficina que filtra webs nginx delante de labweb u Odoo

Por qué un proxy delante de Odoo en lugar de hacer que Odoo escuche en 0.0.0.0:80:

  • Los puertos por debajo de 1024 requieren privilegios de root, y Odoo corre como odoo, sin privilegios.
  • nginx se encarga de HTTPS con el certificado; Odoo sigue hablando HTTP en local.
  • Una IP y un puerto 80 pueden llevar a programas distintos según el nombre pedido (server_name).
  • La documentación de Odoo (Deploying Odoo) asume un proxy delante.

Estructura de la configuración

El fichero principal es /etc/nginx/nginx.conf. Tiene directivas simples (nombre valor;, siempre terminadas en ;) y bloques (nombre { … }). Un bloque es un contexto, y cada directiva solo vale en ciertos contextos.

Contexto Qué contiene
Principal (fuera de todo bloque) Ajustes globales: user www-data, error_log, include de módulos
events { } Cómo atiende conexiones (worker_connections)
http { } Todo lo de HTTP: logs de acceso, tipos de fichero y los sitios
server { } (dentro de http) Un sitio: en qué puerto escucha y para qué nombre
location { } (dentro de server) Qué hacer con las peticiones de una ruta

include inserta el contenido de otros ficheros en ese punto. nginx.conf de Ubuntu tiene cuatro:

Línea Contexto Qué carga
include /etc/nginx/modules-enabled/*.conf; Principal Módulos: extensiones de nginx. Vacío en una instalación básica
include /etc/nginx/mime.types; http Tabla de tipos de contenido por extensión (.html, .png…)
include /etc/nginx/conf.d/*.conf; http Ajustes HTTP comunes. Vacío por defecto
include /etc/nginx/sites-enabled/*; http Los sitios, un fichero cada uno

Sitios disponibles y sitios activos

Organización propia de Debian y Ubuntu; para nginx solo existe la línea include /etc/nginx/sites-enabled/*;.

Directorio Contiene Significado
sites-available/ Los ficheros de configuración reales Sitios escritos, activos o no
sites-enabled/ Enlaces simbólicos a ficheros de sites-available/ Sitios activos: los únicos que carga nginx
  • Activar un sitio = crear en sites-enabled/ un enlace simbólico a su fichero de sites-available/.
  • Desactivar = borrar el enlace (rm o unlink). El fichero original queda intacto.

Un enlace simbólico es un fichero que apunta a otra ruta, como un acceso directo. En ls -l empieza por l y muestra nombre -> destino. Borrarlo no borra el destino. Con ln -s, el primer argumento es el destino y el segundo el enlace; con ruta absoluta en el destino, el enlace no depende del directorio desde el que se cree.

El paquete deja un sitio activo. Al instalarse, nginx arranca, queda habilitado y activa default: escucha en el 80 con default_server y sirve ficheros de /var/www/html, la página «Welcome to nginx!». Los puertos los abre cada sitio con su listen: sin ningún sitio activo, nginx sigue en marcha pero no escucha en ningún puerto.

Las directivas de un sitio proxy

Directiva Contexto Qué hace
listen 80; server Escucha en el puerto 80 de todas las direcciones IPv4
listen [::]:80; server Lo mismo en IPv6. [::] = todas las direcciones IPv6; los corchetes separan la dirección (que lleva :) del puerto
server_name NOMBRE; server Para qué nombre de dominio es el sitio. Sin él, o con _, no corresponde a ninguno concreto
location / { } server Agrupa lo que se hace con las rutas que empiezan por /
proxy_pass http://127.0.0.1:8080; location Reenvía la petición a esa dirección

listen acepta un puerto (80) o una dirección con puerto (0.0.0.0:80, [::]:80). listen :80; no es válido. Con un solo sitio, default_server no hace falta: ese sitio atiende todas las peticiones.

location compara por prefijo. La ruta viaja en la primera línea de la petición (GET /health HTTP/1.1). location / encaja con cualquier ruta que empiece por /, es decir, con todas. Con varias location, nginx elige el prefijo más largo que encaje.

127.0.0.1 y no localhost en proxy_pass. localhost es un nombre y en Ubuntu resuelve a 127.0.0.1 y a ::1 (/etc/hosts). Si el servicio solo escucha en 127.0.0.1, nginx puede probar antes ::1, fallar y dejar errores en el log. Regla: en proxy_pass, la misma dirección en la que escucha el servicio según ss.

Varios sitios en el mismo puerto

Con dos sitios en el 80, nginx mira la cabecera Host de cada petición y la entrega al bloque cuyo server_name coincide. Si no coincide ninguno, la recibe el sitio por defecto: el que lleve default_server en su listen o, si ninguno lo lleva, el primero que carga nginx. sites-enabled/ se carga por orden alfabético.

Petición Sitio que la atiende en el VPS
http://odoo.mlozano.dev odoo (server_name odoo.mlozano.dev)
http://89.58.45.111 o cualquier otro nombre labweb: sin server_name, y carga antes que odoo

Una directiva sin ; puede dar otra configuración válida. nginx lee hasta el siguiente ;. server_name odoo.mlozano.dev sin ;, seguido de listen 80;, se lee como server_name odoo.mlozano.dev listen 80;: un server_name con tres nombres y ningún listen IPv4. nginx -t no lo detecta.

El recorrido de una petición

  1. El cliente pide http://89.58.45.111. Sin puerto en la URL, http:// implica el 80; lo decide el cliente.
  2. El kernel del VPS recibe el SYN para el 80 y entrega la conexión a nginx, que escucha allí.
  3. nginx lee la ruta, la encaja en una location y abre una segunda conexión TCP, desde el propio VPS, hacia la dirección de proxy_pass.
  4. El servicio de detrás responde a nginx, y nginx reenvía la respuesta al cliente.

Consecuencias de que haya dos conexiones:

  • El servicio de detrás ve como origen 127.0.0.1, no la IP del visitante. nginx sí la conoce.
  • La cabecera Server: de la respuesta la pone nginx, aunque el cuerpo sea del servicio.
  • Las versiones de HTTP pueden diferir a cada lado: por defecto nginx habla HTTP/1.0 con el servicio de detrás y HTTP/1.1 con el cliente.

Aplicar cambios

nginx lee la configuración al arrancar y la guarda en memoria. Cambiar ficheros, crear enlaces o borrarlos no tiene efecto hasta que se le pide releerla.

Acción Qué hace Cuándo
nginx -t Lee toda la configuración, incluidos los include, y comprueba la sintaxis sin tocar el nginx en marcha Siempre, antes de recargar
reload El maestro relee la configuración y sustituye a los workers sin cortar conexiones. Si la configuración nueva tiene errores, la rechaza y sigue con la anterior Tras cualquier cambio
restart Para nginx por completo y lo arranca Casi nunca. Corta conexiones, y con un error en la configuración nginx no vuelve a arrancar

nginx -t comprueba la sintaxis, pero no abre puertos: un listen en un puerto ocupado pasa la prueba y falla al recargar.

Procesos. Un maestro, de root, que lee la configuración y abre los puertos, y varios workers, del usuario de user (www-data), que atienden las conexiones. En un reload, el PID del maestro se mantiene y cambian los de los workers; en un restart cambian todos.

Errores: dónde está el fallo

Lo que ve el cliente Dónde está el problema
Connection refused Nadie escucha en el puerto de entrada: nginx parado o ningún sitio con ese listen
502 Bad Gateway nginx funciona; el servicio de detrás no responde. Gateway es nginx haciendo de pasarela

El 502 dice dónde mirar; la causa está en /var/log/nginx/error.log. Las peticiones atendidas se registran en /var/log/nginx/access.log.

Fragmento de una línea de error.log Significado
[error] Nivel de gravedad ([notice] es informativo)
connect() failed (111: Connection refused) La causa: el kernel rechazó la conexión de nginx con el servicio
while connecting to upstream Upstream = el servicio de detrás
upstream: "http://127.0.0.1:8080/" A qué dirección intentaba conectar: identifica qué servicio falla
client: IP La IP pública del visitante
server: El server_name del sitio; vacío si no tiene

Orden de diagnóstico de un 502: curl (confirma el 502) → error.log (causa y upstream) → systemctl status del servicio (parado o caído) → ss (si alguien escucha en su puerto) → journalctl -u del servicio (por qué se cayó).

La corrección tiene dos piezas y hacen falta las dos:

Pieza Dónde Qué hace
proxy_set_header location / del sitio de nginx nginx añade una cabecera con cada dato: X-Forwarded-Host, X-Forwarded-For, X-Forwarded-Proto
proxy_mode = True odoo.conf Odoo sustituye lo que ve en la conexión por lo que dicen esas cabeceras. Sin esta opción, las ignora

Es la recepcionista que, al pasar una llamada interna, añade una nota con quién llama y a qué número marcó; y el empleado al que se le dice que se fíe de esas notas.

Por qué Odoo no se fía por defecto. Cualquiera puede escribir esas cabeceras. proxy_mode es seguro solo porque Odoo escucha en 127.0.0.1 (http_interface): únicamente un proceso del propio VPS, nginx, puede hablarle. Odoo no comprueba quién le habla; la seguridad la da quién puede llegar hasta él. Además, nginx neutraliza las notas falsas del visitante: proxy_set_header sustituye X-Forwarded-Host y X-Forwarded-Proto, y $proxy_add_x_forwarded_for añade la IP real al final de la lista, que es el valor que lee Odoo.

Variables de nginx. Las que empiezan por $ las rellena nginx para cada petición; no se definen. Cada módulo documenta las suyas en su apartado Embedded Variables (índice: https://nginx.org/en/docs/varindex.html).

$http_host La cabecera Host tal cual llega, con puerto si lo lleva. En general, $http_ + nombre de la cabecera en minúsculas con _
$host El nombre de Host, sin puerto y en minúsculas; si falta, el server_name
$remote_addr La IP de quien abrió la conexión con nginx
$scheme http o https, según el listen por el que llegó
$proxy_add_x_forwarded_for El X-Forwarded-For recibido, con $remote_addr añadida al final

21. Websocket de Odoo detrás de nginx

Qué es

Una petición HTTP es una carta con su respuesta. Un websocket es una llamada telefónica: el navegador la abre una vez y queda abierta, y el servidor puede hablar cuando quiera. Odoo la usa para las notificaciones en vivo (mensajes de Discuss sin recargar), en la ruta /websocket.

La llamada empieza como una petición HTTP/1.1 normal con dos cabeceras, Upgrade: websocket y Connection: Upgrade, que piden convertir la conexión. Si el servidor acepta, responde 101 Switching Protocols y a partir de ahí la conexión ya no es HTTP.

Odoo no abre el websocket desde la página, sino desde un SharedWorker: un proceso del navegador en segundo plano compartido por todas las pestañas de Odoo (una sola llamada aunque haya cinco pestañas). Sus peticiones no aparecen en la pestaña Network de la página. Su código se descarga de /bus/websocket_worker_bundle.

Por qué falla sin configuración

Upgrade y Connection son cabeceras hop-by-hop: valen para un salto y nginx no las reenvía al servidor de detrás. location / atrapa /websocket (es prefijo), así que la petición llega a Odoo, pero sin esas dos cabeceras: Odoo recibe un GET normal en una ruta que solo acepta websockets y responde 400 Bad Request. Una centralita que pasa la llamada pero cuelga antes de conectar.

Además, nginx habla por defecto HTTP/1.0 con el servidor de detrás (§18), y la conversión solo existe en HTTP/1.1.

location /websocket aparte

Un bloque server puede tener varios location. Para cada petición, nginx usa el del prefijo más largo que coincida; el orden en el fichero no importa:

Ruta pedida location que la atiende
/web/login /
/websocket?version=18.0-7 /websocket (coinciden los dos; gana el más largo)

Por qué un bloque aparte y no añadir las cabeceras a location /:

  • El trato especial queda solo en la ruta que lo necesita; el resto del tráfico (páginas, imágenes, PDF) sigue igual. Una ventanilla de paquetes urgentes no cambia el proceso de la ventanilla general.
  • Con workers, Odoo atiende los websockets en otro puerto (8072). Ese día solo cambia el proxy_pass de este bloque.
Directiva Por qué
proxy_pass http://127.0.0.1:8069; Con workers = 0, el mismo puerto que el resto
proxy_http_version 1.1; La conversión exige HTTP/1.1. Necesaria en nginx anterior a 1.29.7 (el VPS tiene 1.24.0). Solo en este bloque: location / funciona con HTTP/1.0
proxy_set_header Upgrade $http_upgrade; Reenvía la petición de conversión del navegador
proxy_set_header Connection $connection_upgrade; La acompaña: upgrade si el navegador pidió conversión, close si no
Las mismas X-Forwarded-* que location / Los proxy_set_header de un location no se suman a los de otro: sin repetirlas, Odoo no conocería en esta ruta la IP ni el esquema reales

El ejemplo de Deploying Odoo no lleva proxy_http_version 1.1; la documentación de nginx (WebSocket proxying) sí, para versiones anteriores a 1.29.7. Se confirma en la documentación de la versión instalada (nginx -v). Las líneas add_header Strict-Transport-Security y proxy_cookie_flags del ejemplo son otra cosa (endurecimiento con HTTPS) y se añaden aparte.

map: definir $connection_upgrade

$http_upgrade la rellena nginx (cabecera Upgrade recibida). $connection_upgrade no existe: hay que definirla, y sin ella nginx -t falla con unknown "connection_upgrade" variable.

map es una tabla de traducción: según el valor de una variable, da valor a otra.

map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
Si $http_upgrade es… $connection_upgrade vale…
Cualquier valor (websocket) upgrade
Vacío ('') close

Dónde va. map solo vale en el contexto http, fuera de todo server. include funciona como copiar y pegar: nginx sustituye la línea por el contenido de los ficheros indicados. El fichero de sitio entra en http por include /etc/nginx/sites-enabled/*;, que está dentro del bloque http { } de nginx.conf. Por eso el map se escribe al principio del fichero de sitio, antes del primer server {, y sin envolverlo en http {: quedaría un http dentro de otro, y nginx no lo admite. Los ejemplos que empiezan por http { muestran un nginx.conf completo, no un fichero de sitio.

Comprobarlo en el log

nginx escribe la línea de access.log cuando la petición termina. Una petición normal termina en milisegundos; un websocket que funciona queda abierto y su línea aparece al cerrarse (al cerrar todas las pestañas de Odoo).

Código en access.log para GET /websocket Significado
400 Odoo rechazó la petición: faltan las cabeceras o HTTP/1.1
101 Conversión aceptada: websocket funcionando

grep websocket también encuentra /bus/websocket_worker_bundle (el código del worker, normalmente 304); grep 'GET /websocket' separa las dos.
